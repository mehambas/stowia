# How Stowia works

Stowia is a menu bar app (`LSUIElement`) written in SwiftUI and AppKit, with no dependencies. `StowiaCore` holds everything that can be tested without the interface: clips, reading and restoring the clipboard, the history on disk, image previews, version checks and the import from Sakla. The `Stowia` target holds the panels, the settings and the update download.

## Saving what you copy

A timer compares `NSPasteboard.general.changeCount` every 0.65 seconds. Copies faster than that can be missed, and what was on the clipboard at launch is not saved. When the count changes and saving is not paused, Stowia reads the clipboard unless

- any item carries one of the markers from [nspasteboard.org](http://nspasteboard.org) (`org.nspasteboard.ConcealedType`, `TransientType`, `AutoGeneratedType`) or one of the older markers some apps still write (`de.petermaurer.TransientPasteboardType`, `Pasteboard generator type`, `com.agilebits.onepassword`, `net.antelle.keeweb`, `com.typeit4me.clipping`),
- the app in front is excluded (1Password 7 and 8, Bitwarden and Apple Passwords by default),
- an item has none of the kept types (plain text, RTF, HTML, PNG, TIFF, file and web URLs), or
- the copy is larger than 25 MB.

Clips that Stowia itself puts on the clipboard carry the marker `com.hamzabasaran.stowia.restored`, so pasting from the history doesn't add a copy of it.

Each clip is identified by a SHA-256 of all its items and types. Copying something again moves the existing clip to the top and keeps its name and star. A clip is a link when it is a single http or https address, an image when it has PNG or TIFF data or every file in it is an image, a file when it has file URLs, and text otherwise.

## Storage

The history lives in `~/Library/Application Support/Stowia` (permissions 0700): `history.json` lists the clips with their text, name, source app, dates, star and size, and `<id>.clip` holds the copied items as a binary property list (0600). The index is written atomically before the clip files of deleted entries are removed, and `.clip` files the index doesn't know, left by an interrupted write, are removed after the next successful write. A history that can't be read is left untouched and saving stops, with a message in the panel.

Limits are applied from the newest clip down: clips older than the retention time, beyond the maximum count or beyond the size limit are removed after each copy and once a minute. Favorites are never removed by the limits or by Clear History. For files only the location is kept; a moved or deleted file can't be restored.

Settings, the menu bar position and the window frame are in `~/Library/Preferences/com.hamzabasaran.stowia.plist`.

Stowia was called Sakla before its first release. On the first launch it copies Sakla's history and settings, if there are any and Stowia has none yet, and leaves the originals in place.

## Pasting

Return copies the selected clip to the clipboard, brings back the app that was in front before the panel opened, and posts ⌘V to it once that app is active again and no modifier key is still held. Posting the key needs Accessibility access; without it the clip is only copied. ⇧Return puts only the plain text on the clipboard. Image previews are decoded at the size they are shown, in the background, with a 32 MB cache.

## Updates

Stowia asks GitHub for its latest release 10 seconds after launch and then whenever an hourly tick finds that 24 hours have passed since the last check. The time of the last check is stored, so restarts don't check again, and **Check for updates automatically** in Settings › Updates turns the check off. The request is `GET https://api.github.com/repos/mehambas/stowia/releases/latest` on an ephemeral URL session without cookies, cache or credentials, with a 15-second timeout. Besides the address it sends only `User-Agent: Stowia/<version>`, `Accept-Language: en` and the standard Accept headers: no identifiers, system details or usage data. Any failure (no published release, offline, timeout, rate limit) counts as no news. Automatic checks stay silent about it; **Check for Updates…** in the ⚙ menu and **Check Now** in Settings › Updates always say what they found.

The release's tag (`v0.2.0`) is compared with `CFBundleShortVersionString` number by number, so 0.10.0 is newer than 0.9.0. A newer release puts a dot on the ⚙ button, **Update to 0.2.0…** at the top of its menu and a row with **Release Notes** and **Download and Install** in Settings › Updates; the offer is stored until a later check replaces it. **Download and Install** downloads the asset `Stowia.dmg` to the temporary folder and compares its SHA-256 with the asset `Stowia.dmg.sha256`. If the checksum is missing or does not match, the download is deleted and the release page opens in the browser instead. A verified disk image opens in Finder and Stowia quits: it is not notarized, so it cannot replace itself, and Finder won't replace a running app. The user drags the new version to Applications.

To try the whole flow, serve a release from a local server and start the demo with the testing variables:

```sh
STOWIA_FAKE_VERSION=0.0.1 STOWIA_UPDATE_BASE=http://127.0.0.1:8000 dist/Stowia.app/Contents/MacOS/Stowia --demo
```

`STOWIA_FAKE_VERSION` pretends to be another version. `STOWIA_UPDATE_BASE` replaces `https://api.github.com/repos/mehambas/stowia`, so the server answers `/releases/latest` with GitHub's JSON (`tag_name`, `html_url`, and `assets` whose `browser_download_url`s point back to the server). With either variable set, Stowia checks 10 seconds after launch whatever the last check was, and stores neither the check time nor the offer.

## Development

```sh
swift test --disable-sandbox
bash scripts/build.sh
open dist/Stowia.app
```

`scripts/build.sh` builds a universal app (Apple silicon and Intel) into `dist/Stowia.app` with its English and Turkish strings. macOS ties the Accessibility permission to the app's signature. An ad hoc signature changes with every build, so macOS asks again after each rebuild. `scripts/make-certificate.sh <backup folder>` creates a self-signed “Stowia Self-Signed” certificate in the login keychain, which `build.sh` then uses; `STOWIA_SIGN_IDENTITY` picks another identity, and `-` forces ad hoc signing. Releases must always be signed with the same certificate. Keep the backup the script writes: builds signed with a new certificate lose the permission users granted.

The interface is written in English. Turkish is in `Resources/tr.lproj/Localizable.strings`, and English plurals in `Resources/en.lproj/Localizable.stringsdict`. To see another language, start the app with `-AppleLanguages '(tr)'`.

### Demo mode and self-check

```sh
dist/Stowia.app/Contents/MacOS/Stowia --demo
dist/Stowia.app/Contents/MacOS/Stowia --demo --self-check /tmp/stowia-check
```

`--demo` shows sample clips from a temporary folder. It doesn't watch the clipboard, doesn't import from Sakla and saves no settings; using a clip still copies it. `--self-check` additionally walks through the panel and the library: the panel's size, search by name, favorites, focus, arrow keys, Escape, reopening, closing on an outside click and keeping the selection in the library. It writes `checks.json` and screenshots of the panel, an image preview, the library and both ends of the settings, then quits.

The tests cover favorites, persistence across launches, duplicates, the age, count and size limits, clearing and the removal of clip files, Turkish search, an unreadable history, concealed and oversized clips, rich and plain text, several files and images, image previews, the import from Sakla, versions, GitHub's release answers and checksum files. They use their own named pasteboards and temporary folders, never the clipboard or your settings.

### Demo animations

```sh
bash scripts/build.sh && scripts/make-demo.sh
```

`--capture-demo` plays a short session in the panel with the demo clips and saves each step as a frame, drawn below a menu bar on a dark and a light background. The panel stays off screen and never becomes the key window, so it doesn't take what you type meanwhile. `make-demo.sh` turns the frames into `docs/images/demo-dark.gif` and `demo-light.gif` with ffmpeg.

### Icon

`Resources/Icon` holds the icon sources: the 1024 px artwork, simplified artwork for 16 and 32 px, the layers, the menu bar icon and the GitHub social preview. `Resources/AppIcon.icon` is the Icon Composer version, built from the box and highlight layers with a light and a dark fill; macOS 26 and later derive the tinted and clear styles from it. After changing either, run `scripts/make-icon.sh`: it writes `AppIcon.icns` for macOS 14 and 15 and compiles the `.icon` into `Assets.car` (this needs Xcode 26 or later). Both results are committed, so building the app needs neither Xcode nor the script. To check every style without changing System Settings:

```sh
"/Applications/Xcode.app/Contents/Applications/Icon Composer.app/Contents/Executables/ictool" Resources/AppIcon.icon \
    --export-image --output-file dark.png --platform macOS --rendition Dark --width 512 --height 512 --scale 1
```

The renditions are `Default`, `Dark`, `TintedLight`, `TintedDark`, `ClearLight` and `ClearDark`.

### Releases

```sh
scripts/release.sh 0.2.0
```

The release script sets the version in `Resources/Info.plist`, increments the build number, builds and signs the app with the self-signed certificate, packs it into `dist/Stowia.dmg` and writes its SHA-256 to `dist/Stowia.dmg.sha256`. Attach both files to the GitHub release (tag `v0.2.0`) under these names: the README links `releases/latest/download/Stowia.dmg`, and the update check installs only a disk image whose checksum file it finds next to it.
